### 1.1 Shared contracts — locked before any business logic

These are platform-level contracts. Coordinate with UC2, UC3, UC4 teams before finalising. Once locked, treat as immutable until a formal versioning decision.

**FrameEvent** (consumed from ingestion layer — UC1 does not produce this):

```python
class FrameProvider(str, Enum):
    MINIO = "minio"
    CACHE = "cache"

class FrameEvent(BaseModel):
    event_id: UUID = Field(default_factory=uuid4)
    camera_id: UUID
    frame_seq: int
    timestamp: datetime
    profile: CameraProfile
    frame_provider: FrameProvider
    frame_reference: str        # MinIO object key or Redis cache key
    frame_shape: tuple[int, int]
    camera_shake: bool = False
```

**BaseAnalyticsEvent** (all UC1 internal events inherit this):

```python
class BaseAnalyticsEvent(BaseModel):
    event_id: UUID = Field(default_factory=uuid4)
    event_type: str
    camera_id: UUID
    timestamp: datetime
    track_id: Optional[int] = None
    frame_reference: Optional[str] = None
    frame_provider: Optional[FrameProvider] = None
```

**AlertEvent** (produced to platform alerts:live stream):

```python
class AlertEvent(BaseModel):
    alert_id: UUID = Field(default_factory=uuid4)
    camera_id: UUID
    timestamp: datetime
    severity: AlertSeverity
    alert_type: AlertType
    title: str
    description: str
    source_event_id: UUID
    frame_reference: Optional[str] = None
    frame_provider: Optional[FrameProvider] = None
    status: AlertStatus = AlertStatus.PENDING
    metadata: dict = Field(default_factory=dict)
    # UC-specific context (person_id, zone_id, track_id etc) goes in metadata
    # keeping the base contract clean for all UC teams
```

UC1-internal events (DetectionEvent, RecognitionEvent, ZoneEvent etc) extend BaseAnalyticsEvent. These are UC1's private concern — other teams never touch them.

## Sprint 2 — Ingestion + detection pipeline live

[Directory s2 (1)](https://app.notion.com/p/Directory-s2-1-3e811b19900c80418424dc5b8f9205a7?pvs=21)

**Goal:** A local video file plays, frames flow through ingestion into Redis via the FrameEvent contract, YOLOv8 detects people, bounding boxes land in PostgreSQL.

**Integration note:** Ingestion is a shared platform service per the integration doc. For now UC1 owns and runs its own ingestion for development. During the integration phase, the shared platform ingestion service replaces this — UC1's detection worker only needs to change where it reads FrameEvents from, nothing else.

---

### 2.1 Service 1 — Ingestion

- Test mode — reads local video file via FFmpeg subprocess, `INGESTION_TEST_MODE=true`
- Frame sampler — configurable FPS per camera (default 10fps)
- JPEG encode every frame at quality 85
- Store encoded frame in the `FrameCache` with a configurable TTL (default: 5–10 seconds).
- FrameEvent published to `frames:{camera_id}` Redis Stream using the locked contract schema
    - `frame_provider = FrameProvider.REDIS`
    - `frame_reference = "frames/{camera_id}/{frame_seq:08d}.jpg"`
- Heartbeat published to `heartbeat:ingestion:{camera_id}` every 5 seconds
- Stream MAXLEN 1000 per camera stream
- Camera offline event published to `camera:offline:{camera_id}` if no frames for 10 seconds

### 2.2 Service 2 — Detection worker

- Asyncio consumer inheriting BaseStreamConsumer, subscribes to `frames:{camera_id}`
- Fetches frames using the `frame_provider` specified in `FrameEvent`.
- A single YOLO11m model instance is loaded during startup and reused for all inference requests.
- `BatchManager` accumulates frames and triggers inference when either `batch_size` or `batch_timeout_ms` is reached.
- `TrackerManager` maintains one persistent `ByteTrack` instance per camera, preserving track IDs across frames.
- Detection pipeline:
Frame → YOLO → ByteTrack → Filtering → Face Estimation → DetectionEvent.
- One `DetectionEvent` is produced for every input frame.
- `DetectionEvent` contains:
    - `camera_id`
    - `timestamp`
    - `frame_reference`
    - `frame_provider`
    - `tracks`
    - `inference_latency_ms`
- `DetectionEvent` published to `events:detections` (MAXLEN ~10000).
- Detection results persisted to the UC1 `detection_events` table. *(If you keep UC1-owned persistence.)*
- Message acknowledged only after all required operations (database write and event publication) complete successfully.

## Sprint 3 — Recognition pipeline + enrollment API

**Goal:** An enrolled person walks past a camera, their face is matched against the DB, and a RecognitionEvent with their identity and similarity score appears.

---

### 3.1 Service 3 — Recognition worker

- Asyncio consumer subscribing to `events:detections`
- Skips detections where `has_face: false` or `profile == CROWD_ONLY`
- Frame fetching via `frame_provider` + `frame_reference` (same pattern as detection worker)
- Face crop extraction from frame using `face_bbox` normalized coordinates
- Quality gate — face size, blur (Laplacian variance), pose angle, detector confidence. Thresholds from `camera_config`. Rejects below threshold.
- InsightFace Buffalo-S loaded on startup (full model matrix Sprint 5)
- 512-d ArcFace embedding extracted per face crop
- Recognition sampling — runs on: every 10th frame, new track IDs, quality improvement > 20%
- In-memory embedding cache — numpy matrix loaded on startup, cosine similarity in-process (no DB hit on hot path)
- HNSW index on face_embeddings table for fallback DB search
- Identity tag assigned: enrolled (> 0.75), visitor (0.60–0.75), unknown (< 0.60)
- RecognitionEvent constructed, inheriting BaseAnalyticsEvent:
    - `event_type = "recognition"`
    - `person_id`, `identity_tag`, `similarity_score`, `embedding_id`, `quality_score` as additional fields
- RecognitionEvent published to `events:recognitions`, MAXLEN 10000
- Embedding written to `face_embeddings` table — never raw face image
- shared/audit called synchronously in same DB transaction as embedding write
- Recognition event written to `recognition_events` table
- Subscribes to `cache:enrolled:invalidate` Pub/Sub — reloads embedding cache on enrollment change

### 3.2 Enrollment API (Service 5 — partial)

- `POST /persons` — create enrolled person record
- `POST /persons/{id}/images` — upload face image, extract embedding, average if multiple, publish cache invalidation
- `GET /persons` — paginated list
- `DELETE /persons/{id}` — remove person and embeddings, publish invalidation
- Enrollment validation — reject if no face, reject if multiple faces, reject if quality below threshold
- Embedding averaging — multiple images per person averaged into robust representation
- Enrollment Deduplication —Duplicate Person Check, Duplicate Enrollment Alert, Merge Workflow (optional)

## Sprint 4 — Zones, headcount, alerts fire

**Goal:** Zones are defined, people trigger zone events, an unauthorized person in a restricted zone fires a CRITICAL alert to the platform `alerts:live` stream that appears on a basic dashboard within 5 seconds.

**Integration note:** This sprint is the first time UC1 publishes to the platform `alerts:live` stream. AlertEvent must strictly follow the locked contract — `title`, `description`, `source_event_id`, `frame_reference`, `frame_provider` all required. UC-specific data (person_id, zone_id, track_id, similarity_score) goes in `metadata`.

---

### 4.1 Zone infrastructure

- Zone CRUD API — `POST/GET/PUT/DELETE /zones`
- Polygon stored as normalized (0.0–1.0) coordinate list in JSONB
- Zone type enum — restricted, monitored, safe
- Authorized persons list — `zone_authorized_persons` join table
- On zone create/update, publish `cache:zone_config:{camera_id}:invalidate` to Redis Pub/Sub
- Point-in-polygon utility (ray casting, overlapping zones handled, unit tested)

### 4.2 Worker 4A — Zone Monitor

- Asyncio consumer subscribing to `events:detections`
- Loads zone config from Redis cache, falls back to DB on miss
- Per-frame per-track point-in-polygon check against all zones
- Detects transitions — entered, exited, dwell
- Track state in Redis — `zone:track_state:{camera_id}:{track_id}` TTL 60s
- ZoneEvent written to `zone_events` table and published to `events:zone` stream

### 4.3 Worker 4C — Headcount Aggregator

- Asyncio consumer subscribing to `events:detections`
- Counts persons per zone per frame using zone monitor track state in Redis
- Rolling 30-second average in Redis — `cache:headcount:{zone_id}`
- `headcount_snapshots` written to PostgreSQL every 5 seconds per zone
- On threshold breach — writes `headcount_breach_events`, publishes AlertEvent to `alerts:live`:

```python
AlertEvent(
    camera_id=camera_id,
    severity=AlertSeverity.HIGH,
    alert_type=AlertType.HEADCOUNT_BREACH,
    title="Headcount Threshold Exceeded",
    description=f"Zone '{zone_name}' reached {count} persons (threshold: {threshold}).",
    source_event_id=headcount_event_id,
    frame_reference=latest_frame_reference,
    frame_provider=FrameProvider.MINIO,
    metadata={"zone_id": str(zone_id), "count": count, "threshold": threshold}
)
```

### 4.4 Worker 4B — Restricted Entry Checker

- Asyncio consumer subscribing to `events:recognitions`
- Checks recognized identity against `blocklist` table
- On match — writes `restricted_entry_events`, publishes AlertEvent to `alerts:live`
- Severity scaled by similarity: critical (> 0.90), high (0.75–0.90), medium (0.60–0.75)

### 4.5 Worker 4F — Intruder Classifier

- Asyncio consumer subscribing to `events:zone`
- Joins zone presence with identity from `persons_seen` and `zone_authorized_persons`
- Three cases — enrolled unauthorized, unknown in restricted zone, blocklisted in any zone
- Event deduplication — one IntruderEvent per track per zone entry
- Writes `IntruderEvent` to PostgreSQL before any alert push
- Publishes AlertEvent to `alerts:live` with CRITICAL severity:

```python
AlertEvent(
    alert_type=AlertType.INTRUDER,
    severity=AlertSeverity.CRITICAL,
    title="Intruder Detected",
    description=f"Unauthorized individual detected in restricted zone '{zone_name}'.",
    source_event_id=zone_event_id,
    metadata={
        "zone_id": str(zone_id),
        "track_id": track_id,
        "classification_reason": reason,
        "person_id": str(person_id) if person_id else None,
    }
)
```

### 4.6 Alert pipeline (Service 5 — API Server)

- Dedicated asyncio task subscribes to `alerts:live` permanently
- On new AlertEvent — writes to `alerts` table first (status: pending), then Socket.IO push
- Socket.IO setup — namespace `/alerts`, rooms per camera
- On reconnect — client sends `last_alert_timestamp`, server pushes missed alerts
- Polling fallback — TanStack Query 30s background poll, runs regardless of WebSocket state
- Alert badge always fetched from API, never derived from WebSocket count
- Alert escalation — Celery task scheduled on creation, checks acknowledgment at 2 min and 5 min

### 4.7 Basic dashboard (Service 6)

- Shell layout — sidebar, header with alert badge
- Alert center page — list, severity badge, camera name, timestamp, acknowledge/resolve
- Socket.IO client — connects on load, joins camera rooms, handles reconnect
- No live feed yet

### 4.8 Global Identity Manager skeleton

- Recognition-based linking only (body ReID Sprint 5)
- When RecognitionEvent arrives with person_id, links track_id + camera_id → person_id in `persons_seen`
- Cross-camera headcount uses unique person_id count

### 4.9 Blocklist

- `blocklist` table — person_id nullable, embedding_id nullable, reason, expires_at
- Blocklist CRUD API
- Celery beat job — auto-removes expired entries nightly

## Sprint 6 — Compliance, reliability, hardening, integration-ready

**Goal:** System is DPDP Act aligned, production-reliable, and integration-ready. UC1 delivers clean contract outputs that the platform services layer can consume without modification.

**This is the integration handoff sprint.** By the end of this sprint, UC1 produces well-formed AlertEvents to `alerts:live`, BaseAnalyticsEvent-derived events to internal streams, and structured metrics to PostgreSQL — everything the platform needs to build the unified dashboard, incident management, and reporting on top of.

---

### 6.1 Compliance

- Data retention — `retention_policies` table, Celery beat nightly auto-deletion per category
- DPDP readiness score — consent coverage, retention policy coverage, audit log health, liveness enabled on High Security cameras. Score 0–100 with component breakdown. `GET /compliance/readiness`
- Compliance dashboard page — readiness score, consent status per camera, retention status, audit log feed, breach notification log
- Cascade behavior — person deleted → embeddings deleted → recognition events anonymized → persons_seen anonymized
- Token Service — Generate person token, Generate visitor token, Token lookup APIs, Token-based reporting

### 6.2 Stream reliability hardening

- Consumer group acknowledged reads confirmed on all streams with xack after successful processing
- Stream MAXLEN enforced — `frames:*` = 1000, `events:detections` = 10000, `events:recognitions` = 10000, `events:zone` = 10000, `events:crowd_frames` = 5000, `alerts:live` = no MAXLEN
- Pending entries monitor — xpending checked periodically, re-delivers unacknowledged within 30s
- Catch-up mode — lag > 500 entries triggers catch-up (skip liveness, skip enrichment, write events only), resumes normal at lag < 100
- Stream lag as Prometheus metric — `stream_lag{stream, group}`
- Prometheus alert rule fires when `stream_lag > 1000` for > 60 seconds

### 6.3 Alert reliability

- AlertEvent persisted to PostgreSQL before Socket.IO push — confirmed in Sprint 4, hardened here with transaction retry on DB write failure
- `alerts:live` — no MAXLEN, consumer group xack, pending re-delivery
- Alert escalation confirmed working under load

### 6.4 Operator experience

- Incident reconstruction — `GET /incidents/{alert_id}/timeline` returns ordered event sequence with camera names, zone names, timestamps, snapshot URLs
- Operator feedback loop — "Confirm Identity" / "Not This Person" on uncertain alerts. Confirmed matches update embedding store, rejected matches flagged.
- Per-site behavioral baseline — nightly Celery task computes per-zone, per-hour baseline from 14 days of headcount snapshots. Deviation alerts labeled "Unusual Activity"
- Per-camera false positive rate surfaced in dashboard

### 6.5 Reports page

**UC1's role in integration:**
