# Architecture

**Event-driven microservices.**

Each component is an independently deployable service with its own Dockerfile, dependency set, and scaling configuration. Services communicate exclusively through Redis (async events) or PostgreSQL (persistent state) — never by calling each other directly. There are no synchronous inter-service HTTP calls anywhere in the analytics pipeline.

**Service boundaries are drawn along scaling axes:**

- Stream ingestion scales with camera count
- Detection workers scale with GPU availability
- Recognition workers scale with face throughput
- Event processing workers scale with event volume
- API server scales with dashboard and client connections

Each service owns its domain. No service reads another service's DB tables directly — all cross-domain reads go through the API server.

**Shared internal packages** — three internal Python packages mounted into all relevant containers:

- `shared/schemas` — Pydantic event schema definitions, the contract between all services
- `shared/audit` — audit log writer, synchronous, imported by any service touching biometric data
- `shared/storage` — MinIO client wrapper

---

## Components

### Service 1 — Stream Ingestion

**What it does:** Connects to RTSP camera streams, decodes video, samples frames at a configured rate, pushes raw frames to Redis.

**Stack:** FFmpeg, OpenCV, Redis client

**Scaling:** One instance per camera group. Stateless — can be horizontally scaled by adding instances pointed at different camera subsets.

**Publishes to:** `frames:{camera_id}` Redis stream

---

### Service 2 — Detection Worker

**What it does:** Consumes raw frames, runs YOLOv8 for person and pedestrian detection, runs ByteTrack for persistent cross-frame identity, outputs bounding boxes and track IDs as structured detection events.

**Stack:** YOLOv8, ByteTrack, OpenCV, Redis client, `shared/schemas`

**Scaling:** GPU-bound. Scale by adding GPU containers. Batches frames from multiple cameras for efficient GPU utilization.

**Consumes:** `frames:{camera_id}` Redis stream

**Publishes to:** `events:detections` Redis stream

---

### Service 3 — Recognition Worker

**What it does:** Consumes detection events, crops face regions from bounding boxes, runs InsightFace to extract 512-d ArcFace embeddings, queries pgvector for identity match, tags each detection as enrolled person / visitor / unknown, outputs recognition events.

**Stack:** InsightFace, pgvector client, PostgreSQL, Redis client, `shared/schemas`, `shared/audit`

**Scaling:** GPU-bound. Shares GPU node with detection worker via resource limits. Batches face crops for efficient inference.

**Consumes:** `events:detections` Redis stream

**Publishes to:** `events:recognitions` Redis stream

---

### Service 4 — Event Processing Workers

**What it does:** Consumes recognition and detection events and executes all business logic. Each worker is a separate Celery task but runs within the same service container pool.

**Internal workers:**

- **Zone Monitor** — runs point-in-polygon check per tracked person per frame against configured zone boundaries
- **Restricted Entry Checker** — checks recognized identity against blocklist, emits restricted entry events
- **Headcount Aggregator** — counts persons per zone per frame, maintains rolling average, emits threshold breach events
- **Crowd Density Estimator** — runs CSRNet on zone regions every N seconds, classifies density level, emits crowd events
- **Pedestrian Tracker** — tracks movement vectors, direction, speed, flags behavioral anomalies
- **Intruder Classifier** — combines zone monitor output + enrollment status + blocklist status to classify intruders

**Stack:** Celery, Redis, PostgreSQL, SQLAlchemy, CSRNet, `shared/schemas`, `shared/audit`, `shared/storage`

**Scaling:** CPU-bound. Scale independently from GPU services. Each internal worker type can have its own Celery queue and worker pool.

**Consumes:** `events:detections` and `events:recognitions` Redis streams

**Writes to:** PostgreSQL (all structured events), MinIO (frame snapshots on alerts)

---

### Service 5 — API Server

**What it does:** Serves all REST APIs consumed by the dashboard. Runs Socket.IO WebSocket server for real-time alert pushing. Handles all operator-facing operations — enrollment, zone config, blocklist management, reporting.

**Stack:** FastAPI, SQLAlchemy, PostgreSQL, Redis (cache + rate limiting), Socket.IO, `shared/audit`

**Scaling:** CPU-bound, stateless. Scale horizontally behind Nginx.

**Exposes:**

- REST API — enrollment, zones, blocklist, events, reports, config
- WebSocket — real-time alert stream to dashboard clients

---

### Service 6 — Frontend Dashboard

**What it does:** Operator interface. Live camera feed with bounding box and zone overlays, real-time alert center with acknowledgment flow, zone polygon configuration, enrolled face and blocklist management, daily and weekly exportable reports.

**Stack:** React, TypeScript, Tailwind CSS, TanStack Query, Socket.IO client, Konva.js

**Scaling:** Static build served via Nginx. No server-side state.

---

### Supporting Infrastructure

**PostgreSQL + pgvector** — primary data store. Stores persons, embeddings, events, zones, blocklist, audit logs, config, consent records.

**Redis** — inter-service message bus (Redis Streams), Celery broker, application cache, rate limiting counters.

**MinIO** — object storage for frame snapshots tied to alert events, exported PDF reports, video clips.

**Nginx** — single external entry point. TLS termination, routes to API server and frontend.

**Prometheus + Grafana** — all services expose `/metrics`. Grafana dashboards for queue depth, inference latency, alert rates, DB performance.

**Loki** — structured JSON log aggregation from all services.

**OpenTelemetry** — distributed traces across service boundaries. Mandatory for debugging multi-service alert pipelines.
