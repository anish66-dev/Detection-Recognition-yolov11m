# Events

## Purpose

The Event Processing Framework is responsible for executing all application-specific business logic and analytics. It consumes low-level detection and recognition events, derives higher-level insights, generates alerts, persists structured analytics, and stores evidence snapshots when required.

Unlike the Detection and Recognition Workers, this framework performs **no computer vision inference** (except optional crowd density estimation for high-density deployments). Instead, it transforms observations into actionable events through configurable rules and analytics.

Each analytics component operates as an independent worker, allowing individual scaling, deployment, and fault isolation.

---

# Responsibilities

- Consume `DetectionEvent`s and `RecognitionEvent`s.
- Execute business rules for all UC1 analytics.
- Generate derived analytics events.
- Generate `AlertEvent`s when configured conditions are met.
- Persist structured analytics and alerts to PostgreSQL.
- Capture and archive evidence snapshots for alert events.
- Write audit logs where required.
- Acknowledge successfully processed Redis messages.

---

# Non-Responsibilities

The Event Processing Framework **does not**:

- Detect people.
- Perform object tracking.
- Detect faces.
- Generate face embeddings.
- Perform face recognition.
- Manage cameras or streams.
- Handle authentication or API requests.

These responsibilities belong to the Detection Worker, Recognition Worker, and Platform Services.

# Internal Workers

---

# Zone Monitor

### Purpose

Determines whether tracked persons enter, exit, or remain inside configured virtual zones.

### Consumes

```
DetectionEvent
```

### Processing

- Load configured zone polygons.
- Perform point-in-polygon testing.
- Detect:
    - Zone Entry
    - Zone Exit
    - Dwell Time
- Persist zone transitions.

### Output

```
ZoneEvent
```

---

# Restricted Entry Checker

### Purpose

Detects attempts by restricted individuals to enter protected zones.

### Consumes

```
RecognitionEvent
ZoneEvent
```

### Processing

- Verify recognized identity.
- Check blocklist.
- Validate zone permissions.
- Generate restricted-entry alerts.
- Capture evidence snapshot.
- Persist alert.

### Output

```
AlertEvent
```

---

# Headcount Aggregator

### Purpose

Maintains real-time occupancy statistics for cameras and configured zones.

### Consumes

```
DetectionEvent
ZoneEvent
```

### Processing

- Count unique tracked persons.
- Remove duplicate counts using Track IDs.
- Calculate current occupancy.
- Maintain rolling averages.
- Detect threshold violations.
- Persist occupancy statistics.

---

# Crowd Density Estimator

### Purpose

Estimates crowd density within configured monitoring zones.

### Consumes

```
DetectionEvent
```

### Processing

**Default Mode**

Uses tracked person count:

```
Density = Person Count / Zone Area
```

**High-Density Mode (Optional)**

When configured for environments where person detection becomes unreliable (e.g., railway stations, stadiums), CSRNet is executed periodically to estimate crowd density directly from the image.

### Output

- Crowd density metrics.
- Threshold-based alerts when configured.

---

# Intruder Classifier

### Purpose

Classifies individuals as potential intruders using multiple independent signals.

### Consumes

```
RecognitionEvent
ZoneEvent
```

### Processing

Example rule:

```
Unknown Person
        +
Entered Restricted Zone
        +
Remained Inside > Configured Duration
        =
Intruder Alert
```

Rules are fully configurable and may include:

- Identity status.
- Zone permissions.
- Dwell time.
- Time-of-day restrictions.

### Output

```
AlertEvent
```

# Scaling Strategy

The Event Processing Framework is **primarily CPU-bound**.

Each worker type may run multiple independent instances.

Scaling is achieved by assigning separate Redis consumer groups to different worker types.

Example deployment:

```
Zone Monitor              × 2

Restricted Entry          × 2

Headcount Aggregator      × 2

Crowd Density             × 1

Intruder Classifier       × 2
```

Only the optional CSRNet-based crowd estimation requires GPU resources.

# Failure Handling

### Invalid Event

- Log validation failure.
- Acknowledge message.

---

### Database Failure

- Retry according to retry policy.
- Log error.
- Do not acknowledge until retries are exhausted.

---

### Snapshot Failure

Alert generation continues.

Evidence snapshot upload is retried independently.

---

### Worker Failure

Workers are isolated.

Failure of one analytics worker does not affect the execution of others.

---

### Redis Failure

Reconnect automatically through the shared `BaseStreamConsumer`.

---

# Performance Considerations

The framework should:

- Execute workers concurrently using AsyncIO.
- Keep database connections pooled.
- Minimize duplicate computations.
- Cache static zone configurations.
- Batch database writes where appropriate.
- Avoid unnecessary image retrieval except for evidence snapshots.
